# Ownbase

A personal, cloud-backed developer workspace inspired by Supabase. Built with React, Vinext, Cloudflare D1 (SQLite) and R2.

## Implemented

- Owner-scoped projects protected by hosted ChatGPT sign-in.
- SQL editor with CREATE TABLE, INSERT, SELECT, UPDATE, DELETE, ALTER, joins, multi-statement scripts and result export.
- SQL tables appear in the Table editor with real columns and rows.
- Named JSON document tables; insert, edit, delete, filter and export records.
- Durable file uploads, downloads and deletion, capped at 10 MB per file.
- Project secret keys generated with cryptographic randomness, stored only as SHA-256 hashes; rotation revokes the previous key.
- Server-side JSON HTTP API with project authorization and parameterized queries.
- Responsive dashboard, real project metrics, API examples and error states.

This is an initial backend, not a complete Supabase replacement. It does not provide PostgreSQL, end-user signup/password authentication, row-level policies, realtime, edge functions, backups or a browser SDK. Document tables contain JSON documents; SQL tables have typed relational columns. Reads return at most 500 records, newest first. UI filtering and export operate on those loaded records.

## Run locally

Use Node 22.13+ (Node 24 recommended).

```powershell
npm run install:ci
npm run build
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_narrow_impossible_man.sql
npm run dev
```

The generated initial migration filename may differ; use the SQL file in `drizzle/`. Local migrations and hosted migrations are separate. Local sign-in: `/signin-with-chatgpt?return_to=/`. The portable starter simulates sign-in only in local development. Production identity is supplied by Sites dispatch. Never expose the development server publicly as an authenticated service.

## API

Endpoint: `/api/ownbase`. Owner browser sessions authenticate automatically. Server integrations use `Authorization: Bearer <project-secret>`. The hosted Site is owner-private, so callers outside a signed-in browser additionally require `OAI-Sites-Authorization: Bearer <Sites-service-token>`. A project key alone cannot cross the hosting sign-in boundary. Obtain the Site's service-access credential through its supported Sites connection; never put either secret in browser code. Cross-origin console writes are rejected; this version supports server integrations rather than direct browser SDK calls.

GET query parameters: `action`, `project`, and optionally `table` or `id`.

| Action | Method | Required fields |
| --- | --- | --- |
| state | GET | Owner session; lists owned projects |
| create-project | POST | Owner session, name |
| project | GET | project; lists tables and files |
| create-table | POST | project, name |
| rows | GET | project, table (name or ID) |
| insert | POST | project, table, data (JSON object) |
| update | POST | project, table, id, data (replaces document) |
| delete | POST | project, table, id |
| rotate-key | POST | Owner session, project |
| upload | POST multipart | project in query, file form field |
| download | GET | project, id |
| delete-file | POST | project, id |

JSON writes carry action and fields in the request body. Secret keys permit all data and file operations within their project, but cannot create projects, list workspace projects or rotate secrets. Treat them as administrator credentials. Keys appear once on creation or rotation and remain only in dashboard memory until reloading (hidden when another project is selected).

## SQL editor

Open **SQL editor** in the sidebar, select your project, paste a SQLite query, and click **Run query** (Ctrl/Cmd + Enter also works). On narrow screens the terminal icon opens it; navigation buttons have tooltips. **Table editor → SQL tables** shows the resulting relational tables and rows separately from existing document tables.

The starter script creates a todos table, inserts a row, and selects the data. Templates are available for table creation, inserts, reads and updates. Result tabs correspond to individual statements; SELECT results can be exported as JSON. Drafts and recent query history stay in browser memory for the session (history resets when the editor is reopened). Drafts do not execute automatically.

Each project has an isolated SQLite image, persisted in the cloud control database. SQL cannot query the workspace control tables or another project's data. The real SQLite engine is [sql.js](https://github.com/sql-js/sql.js), with a deterministic edge adapter generated by `node scripts/prepare-sql-engine.mjs`; its MIT license is retained in vendor/. The adapter uses the self-contained JavaScript build to avoid runtime Wasm compilation or network downloads.

This initial SQL feature has a **512 KB database limit per project**, 32,000 characters and 30 statements per run, up to 500 rows per result, a 64 KB result-row limit and 1 MB result budget. It uses SQLite syntax, not PostgreSQL syntax. Workspace SQL endpoints require an owner browser session; project secret keys cannot execute SQL. Application APIs for existing JSON document tables are unchanged.

A script runs against a private image, then saves atomically. Failed scripts leave the saved image unchanged. Concurrent saves use revision checks and reject stale writes with HTTP 409 rather than silently overwriting data. Explicit transaction control, ATTACH/DETACH and PRAGMA statements are not supported in the editor. Foreign keys are enabled automatically. BLOB results display as hex objects.

SQL API actions: sql-execute (POST, project + query), sql-schema (project) and sql-rows (project + table). SQL-created tables are separate from JSON document collections; edit SQL data with SQL statements.

## Deployment

`.openai/hosting.json` declares the Sites project and provisioned DB and BUCKET bindings. The retained Sites Vite integration packages the Worker and schema migrations. Build with the Sites build helper, push matching source, then save and deploy the artifact with Sites. The dashboard remains owner-private.

## Verification

`node --test tests/api.test.mjs tests/sql.test.mjs` exercises the actual transpiled route against in-memory SQLite and an R2 stand-in, including owner isolation, bearer authorization, key rotation, JSON CRUD, file roundtrips and input validation. It does not replace a hosted integration test.
